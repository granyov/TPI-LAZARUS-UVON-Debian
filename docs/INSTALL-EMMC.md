# Прошивка платы целиком в eMMC

После такой установки плата загружается с внутренней памяти: прошивка,
загрузчик и Debian 13 лежат в eMMC, внешний накопитель не нужен. Это основной
вариант для серийных плат.

## Какой вариант выбрать

| Задача | Что брать | Куда пишется |
|---|---|---|
| Прошить новую плату целиком | `tpi-lazarus-uvon-emmc-debian13.tar.xz` | eMMC: прошивка + ОС |
| Поставить ОС на SATA или USB-диск | `tpi-lazarus-uvon-debian13.img.xz` | диск целиком, прошивка остаётся в eMMC |
| Обновить только прошивку | `TPI-LAZARUS-…-v3.7.img` из релиза `v3.7` | раздел `uboot` в eMMC |
| Аварийная загрузка | `…-debian13.img.xz` на microSD | карта, eMMC не трогается |

## Состав комплекта

| Файл | Назначение |
|---|---|
| `MiniLoaderAll.bin` | загрузчик Rockchip, нужен только в режиме MaskROM |
| `parameter.txt` | раскладка разделов eMMC, заводская, посекторно |
| `package-file` | перечень для сборщиков пакетов Rockchip |
| `gpt.img` | готовая таблица разделов, первые 34 сектора |
| `uboot.img` | прошивка TPI, U-Boot 2024.04 v3.7 в роли UEFI |
| `boot.img` | раздел ESP: GRUB и его конфигурация |
| `rootfs.img` | корень Debian 13 с ядром 6.12 |

Раскладка eMMC заводская, менять её не нужно:

```
uboot      8192 секторов @ 16384       4 МБ   прошивка
misc       8192          @ 24576       4 МБ   не используется
boot     131072          @ 32768      64 МБ   ESP
recovery 262144          @ 163840    128 МБ   не используется
backup    65536          @ 425984     32 МБ   не используется
rootfs 12582912          @ 491520       6 ГБ  корень Debian
oem      262144          @ 13074432  128 МБ   не используется
userdata до конца        @ 13336576   22.8 ГБ свободно под данные
```

## Почему в комплекте есть gpt.img

U-Boot соглашается грузиться с раздела только если его тип в GPT равен
`C12A7328-F81F-11D2-BA4B-00A0C93EC93B` — стандартный EFI System Partition,
код `EF00` в `sgdisk`.

Таблица, которую создаёт загрузчик Rockchip из `parameter.txt`, присваивает
разделам собственные типы: у заводской платы раздел `boot` имеет тип
`FBD4486A-E42C-448D-D4E9-7F5C324A7843`. Проверено на живой плате в обе стороны:

- с заводским типом `bootflow scan` раздел не видит вовсе, а `efi_mgr` при
  загрузке уходит мимо eMMC на SATA;
- стоит поменять тип на `EF00`, и тот же раздел появляется в списке
  (`1 efi ready mmc 3 … efi/boot/bootaa64.efi`), а загрузка идёт с eMMC.

Поэтому после записи разделов на смещение 0 кладётся `gpt.img` — та же
раскладка, но с правильным типом у раздела `boot`.

## Установка из Linux

Проверенный путь. Нужен `rkdeveloptool` и доступ к консоли платы.

Ввести плату в режим rockusb из приглашения U-Boot:

```text
TPI-LAZARUS=> rockusb 0 mmc 0
```

Дальше с хоста:

```sh
rkdeveloptool ld                                   # плата видна
rkdeveloptool read-partition uboot backup.img      # на всякий случай
rkdeveloptool write-partition uboot   uboot.img
rkdeveloptool write-partition boot    boot.img
rkdeveloptool write-partition rootfs  rootfs.img
rkdeveloptool wl 0 gpt.img                         # правильные типы разделов
rkdeveloptool rd                                   # сброс
```

Права root не нужны, если пользователь состоит в группе `rkdeveloptool` —
правило udev из `/lib/udev/rules.d/60-rkdeveloptool.rules`.

## Установка из Windows через RKDevTool

Плата вводится в режим **MaskROM** (кнопка или перемычка на плате), RKDevTool
подхватывает `MiniLoaderAll.bin` и дальше работает по таблице:

| Адрес | Файл |
|---|---|
| `0x00000000` | `gpt.img` |
| `0x00004000` | `uboot.img` |
| `0x00008000` | `boot.img` |
| `0x00078000` | `rootfs.img` |

Адреса — те же смещения в секторах, что в `parameter.txt`, записанные как
RKDevTool их ожидает. `gpt.img` пишется **последним**, чтобы перекрыть
таблицу, созданную загрузчиком из `parameter.txt`.

**Честная оговорка.** Windows-хоста у нас нет, и этот путь не проверялся —
проверена только его linux-часть теми же операциями. Смещения и содержимое
файлов одинаковы, но поведение самого RKDevTool при записи на смещение 0
подтвердить мы не можем. Если найдётся Windows-машина, порядок стоит прогнать
и уточнить.

## Режим Upgrade Firmware: единый update.img

`tpi-lazarus-uvon-update.img.xz` — тот же комплект, упакованный в один файл
формата Rockchip. Распаковать и скормить RKDevTool в режиме
**Upgrade Firmware**; плата при этом в MaskROM.

```sh
xz -d tpi-lazarus-uvon-update.img.xz
```

Размер распакованного — 2219749958 Б, SHA-256
`729d67c27bff27958d750935d16fae27e8f98931374df6e744203f44fb0f78df`.

Собирается [`scripts/build-update-img.py`](../scripts/build-update-img.py) без
вендорских утилит: `afptool` и `rkImageMaker` из rkbin не нужны, форматы RKFW и
RKAF реализованы напрямую. Разбор проверен на заводском образе платы —
заголовки и таблица разделов читаются верно, а схема контрольной суммы
(32 байта шестнадцатеричного MD5 в хвосте) подтверждена пересчётом заводского
файла. Посмотреть содержимое любого такого образа можно
[`scripts/rkfw.py`](../scripts/rkfw.py).

**Оговорка та же, что и выше:** сам RKDevTool не проверялся, Windows-хоста нет.
Проверено, что собранный файл имеет корректную структуру и контрольную сумму, и
что его разбирает тот же код, который верно разбирает заводской образ.

**Важно про тип раздела.** `update.img` создаёт таблицу разделов из
`parameter.txt`, то есть с типами от Rockchip. Метод `efi` из списка `bootflow`
такой раздел не видит, а `efi_mgr` — видит, но порядок перебора у него зависит
от сохранённых EFI-переменных и не гарантирован. Чтобы загрузка была
предсказуемой, после прошивки стоит выставить тип:

```sh
sgdisk -t 3:ef00 /dev/mmcblk0      # с самой платы
# либо с хоста: rkdeveloptool wl 0 gpt.img
```

## Первый запуск

Служба `tpi-firstboot` отрабатывает один раз и отключает себя:

1. создаёт ключи хоста SSH,
2. создаёт `machine-id`,
3. растягивает корневую файловую систему на весь раздел — в образе она 2 ГиБ,
   раздел 6 ГБ,
4. задаёт MAC-адреса картам Realtek, продолжая блок, который U-Boot выводит для
   встроенного порта из идентификатора кристалла.

Первый вход — только через последовательную консоль, 115200 8N1, автоматически
под root. Ключей в образе нет намеренно.

## Что проверено на живой плате

- запись `boot.img` и `rootfs.img` в разделы eMMC, прошивка в `uboot` при этом
  побайтно не изменилась;
- загрузка с eMMC: корень `/dev/mmcblk0p6`, `root=UUID` из образа, файловая
  система выросла с 2 до 5.9 ГБ, MAC-адреса встали на места;
- зависимость от типа раздела — в обе стороны, как описано выше;
- `ums` и `rockusb` продолжают работать при установленной Debian.

Не проверялось: RKDevTool под Windows и режим MaskROM (нужен физический доступ
к перемычке).
